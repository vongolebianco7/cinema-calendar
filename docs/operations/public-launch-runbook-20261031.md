# Cinelva 公開・監視・復旧手順

2026-10-31公開予定。これは実行手順であり、公開承認や検証成功の記録ではない。

## 公開前の停止条件

- 公開候補PR #579（最終確認SHA `0a2e7670d0b11ffb5b1a4a93d640a27b6ce3bfc2`）と公開PR #573の最新の正確なSHA、required4ワークフロー、公開証跡、最終CIを照合する。未完了・失敗・別SHAの成功では公開しない。
- ユーザーへ候補SHA、変更、検証、未解決制約、公開URL、復旧先を提示し、明示的な本番実行承認を得る。
- 素材・名称・データ利用条件、問い合わせ/非公開security報告、無料枠の未確認事項を勝手に許諾済み・解決済みにしない。
- 実機iPhone Safariの確認はCI WebKitから独立したゲート。390pxのCIだけで代用したと報告しない。
- productionは既存origin https://cinelva.vercel.app を維持する。origin変更、保存キー・スキーマ変更、実データの移行/削除を含めない。

## 承認前に用意する証拠

1. ライト/ダーク、390/1280、Chromium/WebKitのルート監査・スクリーンショットとエラーログ。
2. 合成データで0点/未評価/未鑑賞、保存・編集・削除キャンセル/確定、独立ブックマーク、再鑑賞、バックアップ/復元を確認。
3. 映画館の県/時間帯/料金条件/上位候補/ポップアップと、遅延ロード後の県/設備フィルター保持を確認。
4. 既存本番の配信SHA・frontend/backend deployment・重要アセットのhash/HTTP状態を読み取り記録し、復旧先にする。過去に観測した80418f05を現在値と決めつけず再取得する。
5. ホスティング/API/DBが無料プランで利用可能かmetadataで確認。秘密値は取得・出力しない。

## 承認後だけ実行する公開

1. 承認対象とPR headが一致することを再確認。承認後に未検証のコードを追加しない。
2. 検証済み準備ブランチをmainへ通常のPR mergeで反映する。force pushしない。
3. 自動デプロイの完了と対象commitを確認する。READYだけで成功とせず、正式URLが対象アセットを配信することを照合する。
4. 公開検証は専用ブラウザプロファイルを使う。利用者の実際の鑑賞記録があるプロファイルでは削除・復元テストを実行しない。
5. ホーム、映画検索、作品詳細、My Cinelva、映画館、カレンダー、規約/プライバシー、PWA案内を確認。初回/既存履歴、テーマ再読込、主要操作、404/コンソール、CSPを確認する。
6. 原稿/スクリーンショットはDEMO表示と画像利用条件を確認する。X等への投稿は公開承認と別に明示指示を得る。

## 無料枠とデータの運用

- 新規有料監視、課金、別アカウントでの枠回避はしない。初日は公開直後・約1時間後・翌日に担当者が上記主要導線を読み取り確認し、#239に結果を残す。この文書だけで自動監視が設定されたとは扱わない。
- Vercelのdeployment失敗/制限、Actions失敗、Neonの停止/転送量、データレジストリの最終成功日時・stale/unavailableを確認する。ブラウザ/APIの負荷試験を本番へ大量送信しない。
- Neonの既知の停止・転送超過に対してcomputeを起動しない。11月1日のリセット後もプラン/実使用量/利用可能枠を確認してから、必要な同期を別途判断する。
- 未確認・取得失敗・配信なしを区別する。古いsnapshotを現在の上映/配信保証と説明しない。更新の失敗を日時書換えだけで隠さない。

## 障害時の復旧

保存/バックアップ破損、主要導線不能、広範なJS/CSPエラー、秘密情報漏洩の疑いは公開継続を止める判断対象。症状・URL・配信SHA・時刻を値や個人データなしで記録し、公開操作を止める。

- コードの復旧は、公開前に記録した正常な配信commitへ戻す通常のrevert PRを優先する。復旧の本番実行も承認範囲を確認し、無断の強制push/DB restore/削除を行わない。
- 検証済みの旧deploymentへの復旧が承認されている場合のみ既存originで切り戻し、実配信を再検証する。新originへの逃避は端末内記録の見え方を変えるため行わない。
- ローカル鑑賞データ、バックアップ、ブックマーク、DBはコードの切戻しのために消去しない。復旧に利用者データの書換えが必要なら停止し、具体的な影響を提示して承認を得る。
- 認証情報の疑いがある場合は値をIssueに貼らず、承認された非公開経路で扱う。pattern scan成功を無漏洩の証明にはしない。
- 復旧後は正式URL・配信SHA・主要操作・保存互換を再確認し、#239へ障害と復旧結果を記録する。
